# docs/16 — ジョブ完了通知の Web Push

- 状態: 実装（Issue #7）
- 前提: docs/12（API トークン権限分離）、docs/14（ジョブ完了のブラウザ通知）、docs/15（PWA）

## 1. 目的と範囲

ジョブが `done` / `failed` になったら、UI のタブを閉じていても購読した端末へ通知する。docs/14 の SSE 通知は残し、Push が使えない環境ではそれだけで動く。

非目的: 購読ごとの通知条件（ジョブ種別のフィルタなど）、SSE 通知の廃止、メールやチャットへの通知、未送信分の再送。`cancelled` は Push しない（開いているタブの SSE 通知は従来どおり出す）。

## 2. 有効化の手順

1. `/ui/` を HTTPS（または localhost）で開けるようにする。`serve` は HTTP で待ち受けるので、HTTPS は前段で用意する。
2. `fleet.yaml` を編集する。

   ```yaml
   api:
     web_push: true        # 既定 false
     job_events: true      # docs/14。併用を推奨
     web_push_subject: "mailto:ops@your-domain.example"   # 推奨（§3）
   ```

   `/push/*` は匿名アクセスを許さないため、`api.token` か `api.tokens` が必要。
3. `serve` を再起動する。初回は VAPID 鍵を生成してログに保存先を出し、起動バナーに `web_push: enabled` を表示する。
4. `serve` を動かすホストから、Push サービス（ブラウザごとに異なる。Apple は `*.push.apple.com`）へ HTTPS で出られることを確認する。環境変数 `HTTPS_PROXY` などは Go の標準どおり使われる。
5. 端末ごとに UI で `read` と `operate` の両スコープを持つトークンを入力し、「通知」ボタンを押して通知を許可する。ボタンが「通知: Push」になれば登録済み。

`job_events` を無効のままにしても Push の登録と送信は動くが、UI は「サーバー側でジョブ通知が無効」と表示し、開いている画面の一覧は自動更新されない。

## 3. VAPID 鍵

- 保管場所: `<state_dir>/vapid.json`（`state_dir` が未指定なら DB ファイルと同じディレクトリ）。権限 `0600`。内容は `{"public_key": "...", "private_key": "..."}`（base64url、パディングなし）。
- 生成: `api.web_push: true` で `serve` を起動し、ファイルがないとき。一時ファイルに書いてから改名するので、`vapid.json` が書きかけになることはない。
- 再起動しても同じ鍵を使う。権限が広がっていた場合は読み込み時に `0600` へ戻し、戻せなければ起動に失敗する。
- ファイルが壊れている・鍵の組が合わない場合は起動に失敗する。自動で作り直すと既存の購読がすべて使えなくなるため。
- 秘密鍵を返す API はない。API サーバーには公開鍵だけを渡す。
- `0600` が守るのは他の OS ユーザーに対してだけ。`serve` と同じユーザーで動くプロセス（local transport のエージェントを含む）は読める。
- バックアップは `fleet.db` と一緒に取る。
- 鍵を作り直す場合（漏えい時など）: `serve` を止め、`vapid.json` を削除し、`push_subscriptions` を空にして起動する。各端末は次に UI を開いたとき、鍵の違いを検出して購読し直す。

  ```bash
  sqlite3 <state_dir>/fleet.db 'DELETE FROM push_subscriptions;'
  ```

### `api.web_push_subject`

Push サービスへ送る VAPID トークンの `sub`（運用者の連絡先）。`https:` の URL か `mailto:` アドレス。省略時は `https://example.com/quota-fleet`（仮の値）。仕様上は任意に近いが、Apple の Push サービスは不正な値（`localhost` のアドレスなど）を拒否すると報告されているので、実在の連絡先の設定を推奨する。この値は Push サービスに渡る。

## 4. API

有効なとき（`api.web_push: true`）は Bearer トークン必須（トークン未設定のサーバーでは 401）。

無効なときは 3 経路とも登録せず、存在しないパスと同じ扱いになる。通常の API 認証が先に働くので、トークンを設定したサーバーではトークンなし・誤ったトークンに 401、有効なトークンに 404 を返す。トークン未設定で `require_auth` もないサーバーは匿名にも 404 を返す。

| メソッドとパス | スコープ | 内容 |
|---|---|---|
| `GET /push/vapid-public-key` | `read` | `{"public_key": "..."}` |
| `POST /push/subscriptions` | `operate` と `read` | `PushSubscription.toJSON()` の形（`endpoint`、`keys.p256dh`、`keys.auth`）。新規は 201、既存は 200（鍵、UA、登録したトークンを更新）。本文は `{"created": true/false}` |
| `DELETE /push/subscriptions` | `operate` | 本文 `{"endpoint": "..."}`。200 で `{"deleted": true/false}` |

- DELETE された endpoint は、行がなかった場合も含め、以後の POST を 410 で拒否する。解除より先に送られた登録（画面側でタイムアウトしたもの、再読み込み前のページや別のタブのもの）がサーバーに後から処理されても、購読は復活しない。期限はない。
- endpoint はそれを知る者が送信先を指定できる URL なので、アクセスログに残らないよう DELETE でも本文で渡す。ログにはホスト名だけを出す。
- 登録の検証: endpoint は `https`、ユーザー情報なし、2048 バイト以内。`p256dh` は P-256 の非圧縮公開鍵、`auth` は 16 バイト。
- UA はリクエストの `User-Agent`（512 文字まで）。

### 保存先

`fleet.db` の `push_deleted_endpoints`: DELETE された endpoint の SHA-256 と削除時刻。URL そのものは残さない。1 つの endpoint につき 1 行で、自動では消さない。送信時の 404 / 410 による削除（§6）は記録しない。

`fleet.db` の `push_subscriptions`: `endpoint`（主キー）、`p256dh`、`auth`、`created_at`、`user_agent`、`token_id`（登録に使ったトークンの SHA-256。用途を区別する接頭辞を付けて計算し、トークンそのものは保存しない。§6）。

## 5. 送信

- 起点は docs/14 と同じ、`serve` プロセス内の状態遷移の発行。`done` / `failed` になった時点で、配信対象の購読（§6）すべてへ送る。親の失敗で連鎖キャンセルされる子は送らない。
- 送信は別の goroutine で行い、状態遷移の処理は待たない。ジョブは順に処理し、1 ジョブの送信は最大 8 並列、1 リクエストは 10 秒で打ち切る。待ち行列は 256 件で、あふれた分はログに残して捨てる。
- ペイロード（暗号化して送る。RFC 8291）:

  ```json
  {"title": "ジョブ #7 完了: <タイトル>", "body": "状態: done（完了）", "job_id": 7, "url": "/ui/jobs/7", "status": "done"}
  ```

  `body` は状態だけの固定文言（`状態: done（完了）` か `状態: failed（失敗）`）。`result_text` と `last_error` は、秘密を含みうるうえロック画面に出るので入れない。内容はジョブの詳細画面で確認する。タイトルはジョブのタイトルを 100 文字まで入れる。`status` は通知の `tag` を SSE 通知と揃えるための項目。
- TTL は 24 時間。端末がそれより長く届かない状態なら、通知は失われる。
- **届け方は 1 回だけ**。再送も永続化もしない。次の場合は届かない: 送信失敗（ログのみ）、`serve` の停止中や停止処理中の遷移、`serve` 以外のプロセスが DB に直接書いた遷移（`job` サブコマンドなど。SSE も同じ）。停止時は、送信中と順番待ちのものを合わせて 2 秒まで待ち、残りは捨てる。
- リダイレクトには従わない。

## 6. 失効した購読の扱い

- Push サービスが **404 か 410** を返した購読は自動で削除し、ログに残す。送信中に同じ endpoint が別の鍵で登録し直されていた場合は残す。
- 削除は送信のときに起きる。ブラウザで解除した直後の送信で失効が返るとは限らず、その場合は後の送信で削除する。
- それ以外の応答（400、403、429、5xx など）とネットワークエラーは、ログに残すだけで購読を残す。403 が続く場合は VAPID の設定（鍵の入れ替え、`web_push_subject`）を確認する。
- UI で通知をオフにすると、サーバーから削除してからブラウザの購読を解除する。片方だけ失敗した場合は、もう片方で通知は止まる。サーバーの削除だけ失敗したときは、後の送信で 410（または 404）が返り削除される。
- サーバーの削除は取り消されない（§4）。ブラウザの解除に失敗して購読が残った場合、次にオンにすると POST が 410 になるので、画面はその購読を解除して新しく購読し直す。解除できなければ「通知: Push 未確認」になる。
- サーバーの削除（2xx）とブラウザの解除のどちらも確認できない場合と、購読の有無を調べられない場合は、ボタンが「通知: 解除未確認」になる。この状態でボタンを押すと解除を再試行し、確認できるまでオンにはしない。ページを開き直したときも解除を試みる。

### トークンとの紐付け

購読は、登録（最後の登録）に使った API トークンに紐付く。送信するのは、そのトークンが現在の設定に存在し、`read` スコープを持つ購読だけ。

- トークンを `fleet.yaml` から削除する、値を変える、`read` を外すと、`serve` の再起動後（API の認証が変わるのと同時）から、その購読には送らない。トークン名だけの変更は影響しない。
- 対象外になった購読は削除せず残し、起動時に件数をログに出す。同じ値のトークンが `read` を取り戻すと配信が再開する。別の有効なトークンで UI を開いて登録し直すと、そのトークンに移る。
- 端末の紛失では、その端末が使っていたトークンを削除するか値を変える。同じトークンを複数の端末で使っている場合は、まとめて止まる。端末ごとに止めたいときは、端末ごとにトークンを分ける。行を消す場合は `push_subscriptions` を `user_agent` と `created_at` で見分けて削除する。
- `token_id` の列がない `fleet.db`（この紐付けより前の版で作ったもの）は起動時に列を追加する。既存の行はどのトークンにも属さないので、UI を開いて登録し直すまで送らない。

## 7. ブラウザ側

- Service Worker（`sw.js`）の `push` ハンドラが通知を表示する。読めないメッセージでも汎用の通知を出す（`userVisibleOnly` の購読では表示が必要なため）。
- クリックは docs/14 の処理（`notificationclick` → `openJob`）をそのまま使う。開く先は `job_id` から組み立て、`url` の値は辿らない。
- `tag` は SSE 通知と同じ `qf-job-<id>:<status>`。タブを開いていて両方届いた場合、後の通知が前の通知を置き換える（本文は後に届いた方になる）。先の通知を閉じた後に届くと、もう一度表示される。
- 「通知」ボタンを有効にすると `PushManager` の購読とサーバー登録も行う。購読はページの読み込み、トークンの入力、ボタン操作のたびに合わせ直すので、サーバー側で消えた購読やサーバーの鍵の変更はそこで回復する。ブラウザが購読を差し替えた場合（`pushsubscriptionchange`）も、次に UI を開くまで登録し直さない。Service Worker はトークンを持たないため。

| ボタンの表示 | 意味 |
|---|---|
| 通知 | オフ |
| 通知: Push | 登録済み。画面を閉じていても届く |
| 通知: 確認中 | 登録を確認している |
| 通知: タブのみ | この環境かサーバーで Push が使えない。開いている画面の SSE 通知のみ |
| 通知: Push 未確認 | 今は登録を確認できない（トークンの権限・認証、通信の失敗など）。以前の登録が残っていれば届く |
| 通知: 解除中 | オフにして、登録を解除している |
| 通知: 解除未確認 | オフにしたが解除を確認できない。通知が届き続ける可能性がある。押すと再試行（§6） |

理由はボタンのツールチップと、有効化した直後のバナーに出る。表の表示は日本語の場合で、英語表示では対応する英語になる（docs/17）。

### 通知に出る内容

Push の文面はサーバーが作るので、UI の表示言語にかかわらず日本語になる（読めないメッセージに出す汎用の通知は英語）。タブを開いていて SSE 通知（表示言語）と両方届いた場合は、後に届いた方が残る。

通知にはジョブの番号、タイトル、状態が含まれ、ロック画面にも表示されうる。結果とエラーの本文は含まない。通信は端末まで暗号化されるが、Push サービスには宛先、時刻、大きさが見える。タイトルに秘密を含めうる運用では、端末の通知プレビュー設定を確認する。

## 8. iOS / iPadOS の制約

- Web Push が届くのは、**ホーム画面に追加した PWA（iOS / iPadOS 16.4 以降）だけ**。Safari のタブでは通知 API がないため、ボタンを押すとこの制約を案内する。
- 手順: Safari で `/ui/` を開く → 共有メニュー → 「ホーム画面に追加」 → 追加したアイコンから起動 → トークンを入力 → 「通知」を押して許可。
- 許可の操作はユーザーのタップが起点である必要がある。「通知: Push 未確認」になった場合は、一度オフにして押し直す。
- トークンは sessionStorage に持つため、アプリを起動し直すと再入力が必要になる見込み。通知の受信自体にトークンは使わない。
- この節の挙動は実機で確認していない。

## 9. 制限

- operate スコープを持つ利用者は、任意の `https` URL を endpoint として登録でき、`serve` はそこへ POST する。operate は信頼できる利用者に限る。
- 購読数の上限はない。
- 同じ端末でもブラウザやインストールしたアプリごとに別の購読になる。

## 10. テストと確認

- 偽の Push サービス（`httptest`）に対して、登録・解除・404 / 410 での削除、暗号化されたペイロードの復号、VAPID 署名、送信が遷移を止めないことをテストする（`internal/push`、`internal/api`、`cmd/quota-fleet`）。
- Service Worker の `push` とページ側の購読処理は node で単体テストする（`internal/ui`）。
- 受け入れ確認（デプロイ後に実機で行う）: HTTPS で UI を開いて「通知: Push」にし、タブを閉じてからジョブを 1 件流して、通知が届くこと。クリックで詳細が開くこと。
