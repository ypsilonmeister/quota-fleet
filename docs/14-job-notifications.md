# docs/14 — ジョブ完了のブラウザ通知（SSE）

- 状態: 設計（2026-11-25 ゆうや承認）
- 前提: docs/07（UI）、docs/12（API トークン権限分離）

## 1. 目的

ジョブが終了状態（done／failed／cancelled）になったら、開いている UI がブラウザ通知を出す。これにより、完了の検知をポーリング型の見守りに頼らなくてよくなる。

非目的: Web Push（タブを閉じている間の通知）、メールやチャットへの通知、イベントの再生（過去分の再送）、購読条件のカスタマイズ。見守り側の縮小は運用側の判断であり、本実装の範囲外。

## 2. サーバー側: SSE エンドポイント

- `GET /events`（ScopeRead 必須）を追加し、`text/event-stream` でジョブの状態遷移を配信する。
- イベント形式: `event: job_status`、データは JSON で `{job_id, title, status, prev_status, agent, host, updated_at}`。終了状態への遷移を主対象とするが、配信自体は全遷移を流し、通知するかどうかはクライアントが決める。
- 発行経路: 状態遷移は serve プロセス内で起きる（ワーカーの complete／fail は API 経由、Gate の遷移も同一プロセス）。遷移を書き込む層からプロセス内のハブ（購読者ごとのバッファ付きチャネル）へ発行し、書き込み側をブロックしない。遅い購読者は切り捨てる（バッファ溢れで切断し、再接続時にクライアントが一覧を取り直す）。
- 接続維持: 25秒間隔でコメント行のハートビートを送る。再接続時の再生（Last-Event-ID）は v1 では行わない。切断明けはクライアントが `GET /jobs` で再同期する。
- 認証: 既存の Bearer（read スコープ）。トークンをクエリパラメータに載せる方式は採らない（ログに残るため）。

## 3. クライアント側（UI）

- EventSource は Authorization ヘッダを付けられないため、fetch のストリーム読みで SSE を受ける小さなクライアントを UI に実装する（再接続とバックオフ込み）。
- 通知の有効化は UI 上のトグル（既定オフ）で行い、有効化の操作時に Notification API の許可を求める。設定は localStorage に保持する。
- 終了状態への遷移を受けたら `new Notification(...)` で通知する。本文はジョブのタイトルと状態（failed は分かる文面にする）。クリックでタブにフォーカスし、対象ジョブの詳細を開く。
- 接続直後に過去分をまとめて通知しない（接続後に起きた遷移だけを通知する）。同一 job_id＋status の重複通知を抑止する。
- 通知と同時に、一覧表示も最新化する（イベントを受けて該当行を更新するか、一覧を取り直す）。

## 4. 設定

- `fleet.yaml` に `api.job_events`（bool、既定 false）を追加する。無効時は `/events` を登録しない（404）。有効化は本番で明示設定する。

## 5. テストと受け入れ

- サーバー: 購読中にジョブを終了状態へ遷移させると対応するイベントが届くこと。無認証が 401、read スコープなしが 403 になること。遅い購読者が書き込み側をブロックしないこと。
- 設定: `api.job_events` の既定値が false で、無効時に `/events` が 404 になること。
- UI: 通知モジュールの単体テスト（既存の UI テスト基盤に乗る範囲で、遷移→通知生成の対応と重複抑止）。
- 既存テストがすべて従来どおり通ること。
- 実地確認（マージ後のデプロイ時に行う）: 本番で有効化し、ブラウザで UI を開いた状態でジョブを1件流し、通知が出ること。
